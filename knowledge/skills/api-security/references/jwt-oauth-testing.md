# JWT 与 OAuth 2.0 安全边界

来源：skills/api-security/references/jwt-oauth-testing.md

## JWT 攻击面

### 算法混淆

JWT 由 Base64URL 编码的 header、payload 与 signature 三段组成。`alg` 描述签名算法，验证端应从可信配置而非令牌自述决定允许的算法。原文的无签名情形描述 `alg=none` 与空签名被接受；RS256 / HS256 混淆描述服务端把 RSA 公钥当作 HMAC 密钥的错误信任关系。判断重点是验证规则与密钥类型是否绑定，而不是令牌能否被解码。

`kid` 是密钥标识，不应具有任意文件路径或可控查询语义。如果它直接决定文件内容或密钥来源，签名边界可能退化为用户控制的查找。保留的观察项是密钥定位来源、规范化、允许值集合和未知标识处理；原路径型注入样例已改写为机制说明。

### 全面验证、弱密钥与声明完整性

原文 jwt_tool 的能力分为：携带 Bearer 令牌的端点响应对照、HMAC 弱密钥评估、声明完整性、RSA/HMAC 算法与密钥混用、嵌入 JWK 的信任关系。工具名仅为历史概念。

`role`、`sub` 的修改影响身份和权限，`exp`、`iat` 影响时间语义；只更改编码后的声明而未获得有效签名，不应被正常验证接受。嵌入 JWK 的关键问题是服务端是否盲目信任令牌自带的验证密钥。观察报告区分：语法可解析、签名有效、声明有效、业务授权有效四层结论。

### 手工 JWT 结构与验证

源代码表达的知识是三段拆分、Base64URL 编解码、声明对象和签名输入之间的关系。解码过程不会自动验证真实性。已知密钥签名、空签名构造和角色/有效期篡改代码改写为上述数据流说明，不保留令牌构造脚本、口令样例或攻击载荷。

## OAuth 2.0 攻击面

### Authorization Code Grant

`redirect_uri` 的解析与校验需要一致：用户信息段、嵌套 URL 和开放重定向会使表面回调与实际接收方不同。`code` 的接收方、绑定客户端和回调是核心证据。`state` 缺失或未绑定会话可能造成登录 CSRF 或账户绑定错位；PKCE 通过 `code_challenge` 绑定授权请求与后续兑换，缺失时授权码截获的影响不同。

回调页面加载第三方资源时，code/token 是否进入 Referer、日志或页面上下文需要以实际请求为据。报告保留泄漏载体及接收方角色，不记录真实令牌。

### Implicit Grant

源材料将此流程标为已废弃但仍有部署。`access_token` 位于 URL fragment，观察浏览器历史、前端脚本、跳转与资源请求中的暴露路径，以及缺少客户端认证时的令牌替换风险。原文将 fragment 与 Referer 泄漏并列，知识页保留该观察主题，但不把它解释为所有浏览器都会直接发送 fragment；应以实际可见的传递路径作为证据。

### Client Credentials Grant

风险包括前端或移动端硬编码 `client_secret`、授予过宽 scope、客户端身份维度缺少限速。长期服务凭证与浏览器公开数据的边界、作用域最小化、失败计数与轮换记录是对应观察项。

### 通用 OAuth 观察项

- scope 从只读到可写的扩大是否经过授权同意和服务端约束。
- 旧 access token 在新资源或状态变化后是否仍可重放，撤销何时生效。
- refresh token 是否无限续期，轮换、过期和复用检测是否一致。
- 租户 A 的 token 在租户 B 是否被拒绝，租户标识是否参与资源授权。
- 日志、URL、Referer、历史记录中是否包含可复用敏感数据。

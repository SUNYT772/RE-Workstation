# CI/CD 管道安全审计

来源：skills/supply-chain-security/references/cicd-pipeline-security.md

## 管道攻击面：STRIDE

| 类别 | 具体信任问题 |
|---|---|
| 欺骗 | 构建身份、签名或来源被冒充 |
| 篡改 | 源码、依赖和构建产物被修改 |
| 否认 | 高影响操作缺少可关联审计日志 |
| 信息泄露 | 日志、缓存或产物包含凭证 |
| 拒绝服务 | CI 资源耗尽或构建遭破坏 |
| 权限提升 | Runner 边界失效或高权限凭证暴露 |

## 审计主题

### Pipeline as Code 配置

GitHub Actions 的 `pull_request_target` 与 `pull_request` 处于不同信任上下文，关键是非可信 PR 内容能否接触高权限 token 或 secrets，而不是单看事件名称。用户可控的 issue 标题等事件字段若直接进入 shell 字符串，会把数据变成代码。安全证据包含事件来源、输入传递方式、代码检出来源和凭证可见范围。

`permissions: write-all` 表示广泛写权限；精细到 `contents: read` 等作用域的声明能表达更小权限。第三方 Action 绑定 commit SHA 比可变 tag 更便于确定所用内容。原 YAML 对比已转为这些信任关系，不复制部署配置。

### 密钥管理

历史提交、工作区、日志和构建产物均可能留下硬编码密钥。密钥清单、使用位置、轮换和最小权限应能够相互关联。OIDC 代表短期工作负载身份，减少长期静态密钥分发；按步骤注入表示只有必要阶段接触秘密。结果记录凭证角色与暴露位置，不记录密钥值。

### 构建完整性

构建溯源记录源码、构建过程和产物之间的关系；原文以 SLSA L2+ 作为证明背景。签名输入是制品，输出是可验证签名或证明，验证依赖受信身份/公钥及制品字节或摘要的一致性。签名存在、签名有效、签名者可信和产物符合预期是不同结论。原签名与验证命令已转为这一输入输出关系。

### Runner 安全

每次全新环境减少跨任务残留；自托管 Runner 需要解释 VM/容器边界与权限。非可信 fork PR、网络出站、跨构建缓存和共享凭证会扩大影响范围。审计证据包含运行器生命周期、挂载和网络权限、缓存隔离、任务之间状态残留，而不只报告托管方式。

### 依赖拉取安全

Node 锁文件、Python 版本冻结、镜像 digest、Go 校验记录分别表达依赖可重复性与内容身份。强制忽略依赖冲突、未验证来源和可变 `latest` 标签削弱可解释性。私有注册表的短期 token 应与仓库/任务范围绑定。这里保留机制，不保留安装命令或运行约束提示。

## 自动化检查结果的知识结构

源示例管道包含：SBOM 生成、OSV 匹配到 SARIF、多源依赖/镜像风险检测、秘密扫描、组件平台接收 SBOM 五类输出。严重度为 HIGH / CRITICAL 的门禁是原示例阈值。SARIF 承载问题位置与规则信息；SBOM 平台关联项目和版本以形成持续监控。对外上传 URL、API Key、安装和启动代码已删除。

## 证据与报告

记录触发事件和输入信任级别、token 权限、secrets 可见范围、第三方代码版本、Runner 隔离与残留、依赖固定、产物身份、签名/溯源、日志与回滚。知识背景为 SLSA Framework、OWASP CI/CD Top 10、GitHub Security Lab，未连接外部服务。

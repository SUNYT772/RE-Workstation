# SBOM 与 SCA 方法论

来源：skills/supply-chain-security/references/sbom-sca-methodology.md

## SBOM 标准对比

| 标准 | 表达形式 | 原文生态语境 | 适用重点 |
|---|---|---|---|
| SPDX | JSON / YAML / tag-value | Linux Foundation、Yocto | 许可证与合规 |
| CycloneDX | JSON / XML | OWASP、Kubernetes | 安全分析与组件关系 |
| SWID | XML | ISO | 企业软件资产标识 |

格式与生态名称按原材料保留；格式选择不证明内容完整或可信。

## SBOM 输入与输出

源码生成方式识别声明依赖，镜像/文件系统方式识别产物中的组件，构建目录与源码关联方式强调产品名、版本和构建关联。原 cdxgen、Syft、SBOM-Tool 示例承载这三种输入输出关系，不保留调用代码。可观察结果是组件身份、版本、许可证、依赖关系、来源及对应产物。

## SCA 能力对比

| 历史工具概念 | 原文速度/数据描述 | 原文可达性描述 |
|---|---|---|
| OSV-Scanner | 极快；OSV 数据 | 不直接提供 |
| Trivy | 快；多源数据库 | 不直接提供 |
| Dependency-Track | 中；NVD、OSV、GitHub | 需额外能力 |
| Snyk | 中；专有数据 | 支持 |
| CodeQL | 较慢；代码级查询 | 支持路径分析 |

这些是原文的比较口径，不是当前产品价格、免费范围或最新规格。实际知识差异在于组件版本匹配与代码路径分析的证据层不同。

## 漏洞优先级策略

原文策略将 CVSS ≥ 9.0、公开 PoC 且可达列为 P0；CVSS ≥ 7.0、有 PoC 且可达列为 P1；CVSS ≥ 7.0 但无 PoC 或不可达列为 P2；其余进入常规管理。原时间口径分别为立即、本周和下一迭代。它是一种历史排期示例，报告需说明实际业务影响和可达性证据，避免只按分数结论化。

## 手工验证的三个证据层

### 实际版本

包管理数据库、包自身元数据、语言运行环境和容器内实际文件可与 SBOM 相互校验。Node 的包元数据、Python 的安装元数据、操作系统的包清单反映不同来源，不应盲信单一 SBOM 字段。

### 公告与受影响范围

CVE 标识、OSV/NVD 条目、GitHub Advisory 和 oss-security 讨论应对照版本上下界、修复状态和特殊配置。相同包名不代表同一供应来源或漏洞范围。

### 实际影响

公开 PoC 的存在与具体部署可受影响不同。认证、本地访问、特定功能启用等利用前提，以及隔离验证中的实际结果，决定可达性解释。保留复核条件与失败结果，不复制运行命令或 PoC。

## 持续监控

原每日更新示例承载 SBOM 刷新、新公告匹配和关键风险门禁三项目标，不保留定时器或管道代码。可观察结果是同一产物前后清单差异、数据库更新时间、告警状态变化及修复验证。源知识背景为 OWASP CycloneDX、SPDX、Google OSV、CISA SBOM Guidance。

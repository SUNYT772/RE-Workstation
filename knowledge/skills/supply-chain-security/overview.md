# 软件供应链安全知识框架

来源：skills/supply-chain-security/SKILL.md

## 适用场景

涉及软件组成、开源依赖、CI/CD、容器镜像、第三方组件合规、构建溯源与制品完整性。原文以美国行政令 SBOM、中国国标和 EU CRA 作为治理背景；此处保留为源材料语境，不构成当前法规核验或实施结论。

## 六层供应链治理框架

| 层次 | 信任对象 | 可观察结果 |
|---|---|---|
| 源码信任 | 上游仓库、维护者、发布历史 | 来源和维护活动是否一致，有无异常变更 |
| 构建管道 | CI/CD 权限、输入、签名 | 可信输入、隔离和门禁依据 |
| 制品分发 | 签名、校验和、SBOM | 产物与声明的构建及组件是否匹配 |
| 运行环境 | 镜像、准入控制 | 实际部署身份、配置和漏洞状态 |
| 持续监控 | CVE、组件版本、调用路径 | 新风险是否影响实际可达路径 |
| 事件响应 | 回滚与受影响版本范围 | 污染制品隔离、替换及恢复证据 |

## SBOM 生成与审计

SBOM 可来自源码、构建目录、镜像或文件系统；CycloneDX 与 SPDX 表达格式，不能替代来源真实性验证。审计包含未知/未授权依赖、停止维护组件、许可证冲突、直接与传递依赖、发布时间线和维护者状态。组件清单需能追溯到具体产物，不应只凭某份清单推断运行版本。

## 软件组成分析（SCA）

漏洞匹配把组件标识和版本关联 NVD、OSV、GitHub Advisory 等信息。源材料中 OSV-Scanner、Dependency-Track、Snyk、Trivy 分别代表快速匹配、持续组件监控、商业可达性评估、镜像/依赖/IaC 多层分析；不规定使用它们或部署服务。结果包含受影响组件、版本范围、公告依据、配置前提和修复版本。

## 漏洞可达性验证

SCA 告警与实际风险不同。源材料给出“约 15% 告警实际可达”的经验性说法，该数值缺少统一样本与测量口径，仅保留为原文判断背景，不作为普遍比例。

风险解释需要把版本确认、CVSS 严重度、公开 PoC 状态、调用路径和运行配置结合。源材料以 CVSS ≥ 7.0 作为优先分析集合。Code Property Graph 切片描述用户输入到漏洞函数的数据/控制流；DEPTEX 中 EPD（Execution Path Dominance）与 LLM 语义判断用于解释路径前提。静态路径、依赖存在与真正可执行路径不能混同。隔离验证所得影响和限制应进入排序依据。

## CI/CD 管道安全

代码提交中的凭证暴露、PR 对依赖和权限的影响、构建产物签名、推送时 SBOM 与证明、部署准入、运行后漏洞监控构成不同控制点，无需固定工具阶段。管道自身关注 Pipeline as Code 注入、Runner 隔离、密钥范围和第三方 Action 的不可变版本绑定。固定 commit SHA 与可移动 tag 的差异在于内容是否可被重新指向。

## 容器镜像安全

镜像包含基础操作系统层、应用依赖与配置三类风险。Dockerfile 的来源、构建权限、版本固定与冗余内容均影响结果。原文 distroless、alpine、slim 的先后是缩小镜像面的历史建议，实际含义是比较业务兼容性与暴露组件；`latest` 缺少不可变身份。签名验证应把可信身份或公钥、制品摘要和预期发布者联系起来。

## 第三方依赖审查

维护者活跃度、近六个月提交、历史恶意植入、传递依赖增加量、许可证兼容和替代组件安全记录都是判断依据。高维护、低依赖数且许可证兼容通常有较低治理负担；低维护、复杂依赖树与许可证冲突需要解释额外风险。这是多因素判断，单个评分不替代证据。

## 证据与报告结构

包含上游及产物身份、SBOM 来源与格式、直接/传递依赖、公告和受影响范围、可达性前提、管道权限与隔离、签名/溯源、修复与回滚、复核结果。原工具链中的 SBOM、SCA、签名、密钥检查、数据流能力全部保留为技术类别；安装、启动、强制阶段和平台注册不进入知识正文。

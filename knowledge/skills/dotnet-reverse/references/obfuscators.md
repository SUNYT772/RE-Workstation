# .NET 混淆器机制与故障特征

来源：skills/dotnet-reverse/references/obfuscators.md

## 适用范围与概念

保留混淆器识别、字符串/资源/方法体加密、anti-tamper、anti-debug、控制流平坦化与恢复失败原因。de4dot、dnSpyEx、dnlib 及内存导出项目是历史名称，自动兼容性描述仅代表原记录经验。

## 核心原理与技术细节

### 总决策表

| 混淆器与原识别标签 | 典型特征 | 原兼容经验与知识重点 |
| --- | --- | --- |
| ConfuserEx 1.x/2.x，cfze | anti-tamper、控制流、字符串、反调试 | 多数曾可自动恢复，完整性与版本影响结果 |
| ConfuserEx 3.x/私改，cfze | 自定义 protector | 静态兼容不完整，运行时内容与 metadata 关系重要 |
| SmartAssembly，sa | 字符串编码、资源压缩、调用隐藏 | 原记录兼容较好，解压和间接调用是重点 |
| Babel.NET，babel | 方法体、控制流、字符串保护 | 原记录支持自动恢复 |
| Eazfuscator.NET，eaz | 字符串/资源、表达式混淆 | 部分版本需单独理解解密器 |
| .NET Reactor，reactor | necrobit、anti-tamper | 新版恢复较困难，关注运行时方法体与 metadata |
| Themida .NET | 外壳与虚拟化 | 原通用托管恢复方式不适配，需要解释本机外壳 |
| Agile.NET/CliSecure，agile | 方法体加密 | 原记录支持自动恢复 |

### 原标准用法所对应的恢复目标

自动识别、显式保护类别、仅探测、批量对象与仅字符串恢复是不同范围。只恢复字符串意味着按解密方法 token 和调用参数解释明文，同时保留原控制流；它并不证明完整 anti-tamper 或所有方法体已经恢复。原参数 `strtyp/strtok` 的信息语义是解密器类型与方法 token，本页不提供命令形式。

### ConfuserEx：特征识别

`<module>` 中标记 `MethodImpl(NoInlining)` 的检查、密集的 `Dictionary<string,T>` 字符串解密调用、switch/state 分派、`.cmp` 压缩资源、乱码类名和方法名、反编译中大量 `int num` 与 switch，都是原记录的候选特征。任意单项都不足以确定具体版本或私改情况。

### ConfuserEx：恢复结果与 anti-tamper

方法体哈希检查可能使修改后的程序在运行时失败。unknown、恢复后打不开和主入口前异常可能对应保护识别不完整、完整性校验、运行时解密或私改 protector。原材料包含抑制检查与运行时内存导出两类处理方式；本页保留其目标差异：前者改变校验行为，后者观察初始化后内容，不复制绕过修改或运行指令。

### 控制流还原后

平坦化 switch/state 恢复为条件和循环，说明可读性提高；残留 state 机意味着部分结构仍需解释。重复处理的历史建议不等于语义正确，关键是恢复前后路径、条件与数据流是否一致。

### SmartAssembly

`SmartAssembly.Runtime.Strong` 字符串编码、`{assembly}.Resources` 压缩资源和 `ProcessCaller`/间接调用是原特征。方法调用隐藏把直接调用的可见性转移到分派层，资源压缩使配置和字符串不直接显现。原“一键恢复”是当时经验，本页不承诺版本通用兼容。

### .NET Reactor：necrobit

necrobit 将真实方法体加密存于资源，运行时解密并注入，离线可见的方法可能仅为空壳。原记录称旧版更易恢复，4.x+ 常失败。初始化后的程序集内容、残留混淆与 metadata 完整性是三个不同问题；内存中已有代码不保证导出文件的元数据已正确重建。

### 字符串解密器手动提取

常见签名角色为 `static string Decrypt(int)` 或带字符串与整数参数的返回字符串方法。高调用频率、常量参数、string 返回类型与方法 token（原例 `0x06000012`）可共同定位候选。若解密器自身也经过平坦化，其控制流与变换算法仍需解释；不能把每个高频 string 方法都当成解密器。

### anti-debug 常见手法

| 观察对象 | 机制 | 解释重点 |
| --- | --- | --- |
| Debugger.IsAttached | 托管调试附加状态 | 返回值如何进入判断 |
| Debugger.IsLogging | 调试日志状态 | 与实际分支的关系 |
| DateTime.Now 差值 | 时间检测 | 时差阈值、调度和调试停顿的影响 |
| CheckRemoteDebuggerPresent 的 P/Invoke | 本机调试状态 | 托管到本机调用及返回值 |
| try/catch 路径选择 | 异常承载控制流 | catch 中可能是真实业务路径 |

原 getter 修改、删除调用与比较的示例不复制为绕过配方；机制、观察字段和“不应把异常块一概视作无用”的判断经验仍完整保留。

## 观察项与判断依据

识别标签、模块初始化器、资源格式、方法体形态、字符串调用参数和运行时值构成相互支撑的证据。保护名称相同并不保证变换相同；私改版本和多层保护可能产生混合特征。

## 故障定位与经验

原“失败退路”转写为四个可解释信息面：保护识别结果是否一致、运行时方法体是否已出现、metadata 是否可解析、解密点是否有可观察明文。运行时值可以回答配置问题，即使整个程序集尚未恢复；反之，名字变可读也不证明所有控制流都已恢复。

## 证据与报告结构

记录保护候选与版本依据、初始化依赖、方法 token、资源与字符串变换、原/恢复内容对应、完整性影响、可读性变化以及仍未解释的路径。不保存真实密钥或可执行绕过材料。

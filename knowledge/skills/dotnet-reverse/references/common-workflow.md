# .NET：IL、状态机与运行时观察

来源：skills/dotnet-reverse/references/common-workflow.md

## 适用范围与概念

本页保留端到端托管分析中的信息关系、IL 保真、字符串恢复、状态机、异常路径、模块初始化器和配置来源。原始样本、恢复样本与修改样本代表不同证据阶段，不要求按固定阶段工作。

## 核心原理与技术细节

### 完整工作流所承载的信息关系

托管身份解释为什么存在 IL；混淆器判断解释为何离线视图不完整；恢复内容便于静态理解；运行时值验证初始化与解密假设；修改差分解释行为变化。原 target、target-clean、target-patched 命名用于区分这三种内容身份，而非要求运行或生成目标程序。

### IL patch 与 C# patch 可靠性

| 维度 | 高层 C# 重编译 | IL 层变更 |
| --- | --- | --- |
| 失败来源 | 缺引用、语法、lambda 重写 | 方法体一致性与指令语义 |
| 信息保真 | 编译器会重新生成 IL | 可限定到逐条指令 |
| 简单常量 | 易阅读，仍涉及重编译 | 可对应原常量加载位置 |
| 判断与控制流 | 可能重写周围结构 | 更接近原分支和返回 |
| async/yield/闭包 | 编译器生成代码难以往返重构 | 状态字段和 MoveNext 仍可直接解释 |

原“IL 更可靠”指相对于反编译再重编译的保真优势，不意味着所有 IL 改动天然正确。未改位置的保留与修改位置的可观察效果属于两个验证面。

### 典型 IL patch 模式的语义

原例中的 `call` 形成返回值，布尔加载形成真假值，`brfalse.s` 根据栈上值决定分支，`ret` 结束方法，`nop` 保持空操作，`ldstr` 引用字符串 token，`ldc` 表示数值常量，`ldarg` 读取参数。改变判断、返回值、常量和整段校验分别作用于这些语义层；字符串存于资源或经过加密时，文本常量不一定在方法体内。

本页不复制强制通过校验的修改序列。保留的判断依据是：返回类型、求值栈、分支目标、字符串来源和异常区域需要与预期语义一致；简单 C# 常量修改与复杂状态机修改具有不同的保真风险。

### 状态机识别：async/await 与 yield

编译器生成的嵌套类保存状态和跨暂停点数据，`MoveNext()` 按状态字段分派。原 `<>1__state`、case 0/case 1 示例用于表达 await 前后逻辑及状态转移，不能把数值直接套到其他程序。C# 视图可能重构为漂亮的 async 方法，但具体判断实际位于 MoveNext 的某个 case 或状态转移中。

### 字符串解密器提取与 metadata 表示

原 dnlib 代码骨架表达：程序集含类型，类型含方法，只有有方法体的方法才有指令序列；解密器可以由方法 token 标识，调用点包含常量参数，解密结果具有字符串语义。恢复后的明文与调用位置需保持一一对应。

该骨架没有实现反射调用部分，并非完整解密器；知识页不补写执行代码。保留的算法关系是“定位解密器及参数—解释其变换—关联明文与调用位置—比较替换前后语义”。程序集加载或反射会触发代码，是原动态方式的副作用背景，不在本次转写中执行。

### 动态调试要点

方法入口、对象字段、局部变量、观察表达式、字符串内容和运行时变量值分别提供不同证据。异常类型和抛出位置可帮助解释被 try/catch 遮蔽的路径。运行时改值是一种临时状态变化，与磁盘上方法体变化不能混同。

### 异常驱动控制流

原例 `CustomException` 携带 Code，catch 中按 `0x42`、`0x43` 选择真实逻辑。异常在此是状态传递与跳转机制，不能简单移除所有 throw/catch 后仍声称行为等价。观察异常类型、Code 来源、catch 条件和后续数据流，有助于重建真实路径。

### 模块初始化器：Module .cctor

`<module>` 的 `.cctor` 可能承担模块初始化、anti-tamper、字符串或方法体解密，逻辑上可能先于 Program.Main/Startup 的业务行为。初始化器存在不证明一定有保护；校验、资源解密和主逻辑依赖关系才解释为什么后续方法离线不可读或修改后失效。

### 配置、C2 与密钥来源模式

明文 URL/IP 缺失不代表没有网络配置。`byte[]` 字段、内嵌资源、AES/XOR 变换、解密返回值和对象字段能够关联配置来源。原例讨论 AES-256-CBC、Key 与 IV 复用以及 Codegate 2013 两阶段 XOR+AES-CBC；这些是识别特征和实现模式，不保留实际密钥值或新增解密 payload。

配置证据应区分资源原数据、算法识别、解密后字段和运行时使用处。真实密钥内容与 C2 的具体值不进入通用知识页；它们的来源关系和字段角色仍被保留。

## 观察项与判断依据

托管 .NET、Mono/Unity 托管层和 Xamarin 可以共享 metadata/IL 解释；IL2CPP/NativeAOT 的产物属于本机层；本机 loader 加托管内容是两层对象。不能仅因存在 .NET 字符串就给整个文件套用同一工作模型。

## 故障定位与经验

C# 往返编译失败时，引用与编译器生成结构是常见原因；恢复样本打不开时，需要辨别 metadata、完整性和运行时解密；异常看似“出错”时，catch 可能才是主路径。原脚本只提供思路的部分不被伪装为可直接使用的完整方案。

## 证据与报告结构

原产物清单的知识含义为：original 保存原件身份，clean 保存恢复结果，notes 保存混淆器、token、关键方法和配置来源，patched 保存另一个修改版本，il-diff 保存前后 IL 对照。报告应说明这些内容之间的来源关系、分析范围与验证状态，不要求生成可执行或私密资产。

# 字节码、解释语言与约束型语言

来源：skills/reverse-engineering/languages.md

## Python Bytecode Reversing

### 分离奇偶索引的 XOR 校验

原 dis.dis 案例先检查长度，偶数位与 K1 异或比较 p1，奇数位与 K2 异或比较 p2。纯逆关系为 `input[2*i]=p1[i] XOR K1`、`input[2*i+1]=p2[i] XOR K2`。p1/p2 长度、索引范围和最后一个字符应分别核对，不能默认总长度为偶数。具体密钥值不保留。

### 字节码线索

LOAD_CONST 后的 COMPARE_OP 可揭示目标，BINARY_XOR/BINARY_ADD 表达变换，BUILD_TUPLE/BUILD_LIST 可构建目标数组，FOR_ITER 与 BINARY_SUBSCR 体现索引，ord 调用体现字符到整数。字节码栈的输入输出和版本决定 opcode 的真实语义；名字相同或相近不保证版本间完全一致。

## Python Opcode Remapping

### 识别

反编译出现 opcode 错误可能来自重映射、版本错误或封装未还原。PyInstaller 中的修改版 opcode.pyc 与自带解释器是原案例线索。

### 恢复关系

新编号到原编号的映射应由修改版 opcode 定义与相应版本的标准定义对照。重映射、参数宽度、跳转偏移和扩展参数都要一致，才能得到正确栈语义。Hack.lu 2013 案例中的自带解释器理解自身映射，这是解释来源，不构成执行未知解释器的要求。

原资料记 uncompyle6 覆盖 Python 2.x–3.8、pycdc 用于 3.9+；这些是历史项目范围，未作当前版本核验，也不包含编译或安装说明。

## Pyarmor 8/9 静态还原

`PY` 加六位数字的封装、匹配的 pyarmor_runtime 与受保护字节码构成输入材料；Pyarmor 7 及更早的 `PYARMOR` 头属于不同族。`.1shot.` 是原项目输出命名，反汇编与实验性源码应分层评价；矛盾处以真实字节码语义为依据。外层归档、封装和 runtime 归属需要分别确认；原执行文件路径、安装与命令不保留。

## DOS Stub

PE 头之前异常大的 DOS stub 可能是完整 16 位 DOS 程序，校验不一定在 Windows PE 代码内。16 位寻址、DOS 入口和 int 16h 键盘语义是关注点。DOSBox/IDA 是原资料的历史表示名称，不要求运行样本。

## HarmonyOS HAP/ABC

HAP 为 ZIP 包，ABC 为嵌入字节码。原 abc-decompiler 的高层重建可能遇到 SSA/PHI 问题，simple、auto、restructure 是表示复杂度不同的模式。simple 输出可以保留业务逻辑，即使某些方法或高层结构失败也不等于全部失败。

原例 `pages/Index.java` 是业务位置线索；来源、配置与输出版本需要一致，旧输出混入新结果会造成误判。GUI 与批量入口、日志级别、路径引号和目录选项是运行界面信息，本页保留其“结果归属清晰、错误与部分成功分开”的知识目标，不保留调用语法。

## Brainfuck / Esolangs

带、单元位宽、指针、括号匹配和输入结束语义构成解释状态。编译来源如 BF-it 可能带来重复惯用模式。

### 逐字符静态分析（BSidesSF 2026）

原 i-love-my-bf-part1 的逗号表示输入，后续增减链可构造比较常量。连续加的净值按模 256，连续减可对应 `256-minus_count`；混合增减取净值。清零模式使不同字符片段独立；循环乘法需考虑指针移动和源单元消耗，不只是数源码中的加号。

源示例 `[->>+++<<]` 表达把源值的三倍加到右侧目标并清空源，只有相应初始单元条件下才等于简单乘三。分段常量与真实比较操作数对应后，才支持恢复输入。

### 读次数侧信道（BSidesSF 2026）

part2 的正确字符使程序进入下一校验并继续读取，因而已执行逗号数量可关联前缀进展。一个最小解释模型包含 30000 个单元、ptr、ip、输入迭代器、括号双向表、8 位加减、输入计数、循环跳转和停止条件。候选之间同初态及同 EOF 语义是计数可比的条件，更多读取不自动代表任意程序的正确输入。

### 比较惯用式（BSidesSF 2026）

part3 的既有比较片段为 `<[-<->] +<[>-<[-]]>[-<+>]`；源例在匹配处观察 ptr−2/ptr−1 单元，分别关联输入与目标。实际指针相对位置需要上下文证明。`[-]` 清零、`[->+<]` 向右累加并清零源，也是原资料模式。保留的是已有程序语义，不新增 payload。

## UEFI

UEFI 常含 PE32+ 映像，但具体架构与固件模块类型仍需头字段确认。Bootkit 替换加载器、DXE 驱动、Boot Services 协议和自定义 VM 保护解密是源中主题。固件容器、抽出模块与 VM 字节码需要各自的地址和来源关系，不保留提取命令。

## 转译为 C

VM opcode 到 C/IR 的映射需保持寄存器位宽、溢出、内存别名和控制流。XOR、ADD 等虚拟操作可表示为对应运算，编译器的常量折叠、内联和死代码消除可以揭示底层算法；优化后的短代码仍要与原 VM 状态对照，而不是只看可编译性。

## 代码覆盖侧信道（Nullcon 2026 Coverup）

原 PHP/XDebug 材料包含未用代码、死代码和分支覆盖信息；数据相关的 `xored == chr(N)` 分支把中间字节值与执行行关联。coverage JSON 中行号和命中次数可形成发生过的值集合，结合已知明文或 S-box 候选减少输入域。

集合通常丢失位置、顺序与次数，因此不能单凭“发生过”断言某一位置的值。恒时、无数据分支实现不提供相同泄漏。原求解与文件读取代码转为“覆盖行—分支常量—值集合—候选一致性”的证据结构。

## OPAL 函数式语言

.impl/.sign、IMPLEMENTATION/SIGNATURE、嵌套 IF..THEN..ELSE..FI、f1…fN 与 seq[nat]/string/denotation 是识别线索。纯函数意味着无相关副作用，不意味着数学可逆；源中“纯函数都可逆”应修正为检查每一步是否单射、是否丢信息。

对于 `F_final(F_n(...F_1(input)))`，若变换可逆则按逆序处理。原 scramble 的累计偏移依赖未知原值，但总影响模 256 只有 256 类，可枚举聚合偏移 S，并检验由候选重算的 S 是否一致，而不枚举所有原状态。

```text
对每个 S ∈ {0..255}：
  candidate[i] = (decoded[i] - S) mod 256
  S_check = Σ contribution(i,candidate[i]) mod 256
  当 S_check=S 时，再检验其余代换和输出条件
```

## Python 版本特定字节码（VuwCTF 2025）

原 A New Machine 指定 Python 3.14.0 alpha，alpha/beta 与稳定版 opcode 可不同。关键是精确版本与头部、操作码及参数格式匹配，不能把后续正式版当等价。原下载和构建指令移除。

原平方元组校验为 `expected[i]=ord(input[i])²`，逆关系是非负整数平方根；需要验证 `isqrt(v)²=v` 与字符范围，不能对非完全平方数直接截断。

## 非双射代换

S-box 有重复输出时，逆表是 `output→候选输入集合`。`|set(S)|<|S|` 反映碰撞。已知格式、覆盖或时间证据、可打印范围和正向重算都可以缩小候选，但不能用字典的最后一次覆盖静默丢掉其他解。

## FRACTRAN 逆向（Boston Key Party 2016）

状态为整数；按表中顺序选择首个使 `n*num` 可整除 den 的分数，更新为 `(n*num)/den`，无可用分数时停机。ASCII 值可编码为连续素数指数，输出因式分解的指数能解释 I/O。

交换分子分母产生候选逆转移，但 FRACTRAN 的“第一个适用分数”优先级和前驱不唯一会破坏简单逆跑；原案例的成功路径若可逆，仍需检查分数顺序与正向验证。此限定保留原反演主题而不推广成普遍定理。

## 证据与故障定位

核心证据包括解释器版本、字节码映射、栈和带状态、常量来源、非双射候选、覆盖信息损失、聚合状态一致性和正向验证。命令成功、源码可读或一个候选可打印，都不能替代这些对应关系。

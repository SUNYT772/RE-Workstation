# 静态表示、格式恢复与状态观察

来源：skills/reverse-engineering/tools.md

原文按工具组织，本页保留同一组技术对象与子主题，将命令、菜单、API 示例转为输入、状态、表示和核对结果。历史名称帮助对应旧资料，不构成依赖。

## GDB：位置与状态

### 基本状态观察

关注程序入口、main、函数内或绝对位置、继续后的下一状态，以及逐指令进入调用和跨过调用的差别。寄存器、栈、指令窗口和字符串内存提供不同视图；修改寄存器会改变被观察对象，记录中要区分原始状态与修改后的状态。

### PIE 二进制

PIE 的加载基址在进程启动后确定。静态偏移、main 内偏移与运行时绝对地址之间必须有明确关系。原示例使用 main+0xca、main+0x198，属于函数内位置示例，不是通用地址。

### 重复观察与状态序列

原单行自动化命令表达的是“入口状态—选定位置—到达时状态”的可重复关系。技术记录保留样本、输入、模块基址、位置与观察值即可，不需要保留调试器调用代码。

### 内存表示

同一地址可按零结尾字符串、固定长度字符、十六进制字或指令解释。原例分别观察 38 个字符、栈上的 20 个十六进制单位、当前指令指针附近 10 条指令。长度、单位、端序和可读区间是解释结果的必要条件，不能把所有可读字节都视为字符串。

## Radare2：函数和控制流表示

### 基本会话所承载的知识

函数列表、main 反汇编、地址处的状态、重启前后差异和寄存器值，共同描述可执行文件的静态与动态关系。分析得到的函数边界仍需由调用、返回、数据引用和可达性检验。

### 重复候选与 r2pipe 历史示例

原例在同一观察位置比较 0–255 的候选值，并以成功输出筛选。它承载的算法是有限候选域、可复位初态和一致判据；若未固定输入、环境与前缀状态，候选之间的结果不可直接比较。本页不保留启动、寄存器改写或工具调用循环。

## Ghidra：反编译与 IR

### 批量分析的产物

原 headless 示例的产物是文件对应的函数、反编译结果和注释。知识层面的要求是原始地址到分析结果的可追溯关系、同一架构与同一项目版本，而不是项目路径或脚本入口。

### 解密函数的状态模型

解密函数语义恢复需包含代码与数据映射、栈、帧指针、参数寄存器、函数入口、返回边界及输出地址和长度。原 EmulatorHelper 示例在这些状态确定后观察解密字节；缺失初始化、全局数据或 ABI 会产生看似合理的错误结果。

### 函数、引用与注释记录

原 MCP 列表转为三类知识产物：函数/导入/字符串清单、函数伪代码与交叉引用、基于证据的函数/变量语义名。不保留调用标识或运行指令。

## Unicorn：指令语义与混合位宽

### 基本状态

CPU 模型需明确 x86-64 等架构和模式、代码映射区、栈映射区、栈顶、起止 PC。原例使用代码基址 0x400000、栈区 0x7fff0000，这些只是样例布局；真实状态以目标的地址关系为准。

### 64 位与 32 位切换

远返回的栈读取宽度不同：源例 retf 消耗 4 字节 EIP 与 2 字节 CS，共 6 字节；retfq 的例子为 8 字节 RIP 加 8 字节槽位中的 CS，共 16 字节。具体前缀与执行模式影响指令解释，应与实际字节核对。

切换语义不仅是 PC 改变。需要对应的内存、EAX/EBX/ECX/EDX/ESI/EDI/EBP 与 64 位低 32 位、EFLAGS/RFLAGS，以及栈和返回状态。SSE 密集代码还依赖 XMM0–XMM7；遗漏 SIMD 状态会让后续计算失真。源文提到的未实现寄存器警告属于实现覆盖信息，屏蔽警告不能补足语义。

### 指定位置的寄存器轨迹

地址、指令大小和寄存器值构成一条状态记录。原例观察 RSI；这个名称只是目标相关的状态变量。只在指定位置记录可减少无关信息，但需知道该位置相对当前模块的偏移。

### 变化驱动的轨迹

相邻状态中值发生变化时记录 `(PC, old, new)`，可定位数据来源和更新指令。寄存器值未变不表示内存未变；别名、调用副作用和重复写入仍可能有意义。

## Python 字节码

### 字节码结构

`.pyc` 头长随 Python 版本变化，原例跳过 16 字节只适用于相应版本。其后为 code object，含常量、名称、局部变量与字节码。版本错误会同时影响解析、opcode 含义与控制流。

### 常量与 LOAD_CONST

LOAD_CONST 对应常量池对象，可能是整数、字节串、字符串或嵌套代码对象。常量的用途需要和后续运算、索引和调用相连；不能只凭可读片段认定答案。

### Pyarmor 8/9（历史名称 1shot）

源资料范围是 Pyarmor 8.x–9.x 的 `PY` 加六位数字头，而早期 `PYARMOR` 头的 7 及以前不在同一覆盖范围。runtime 库与封装版本是解释输入；还原反汇编与实验性反编译源码的可信度不同。原文的路径存在、递归输入和输出目录要求属于运行配置，已改为样本族、runtime 归属与输出阶段的知识区别。

## WASM

### 线性内存与高层表示

WASM 到 C 的表示可让函数、循环与内存访问更易读，但仍需保留 WASM 的整数位宽、陷阱和线性内存语义。`w2c_memory` 表示线性内存，`wasm_rt_trap(N)` 表示运行时错误；`flagChecker`、`validate` 等导出名可作为入口线索。

## Android APK 与相关格式

### 包与代码材料

APK 中 XML 资源、DEX 字节码、assets 和 native 库属于不同层次。解码后的 XML、Java 近似表示和原始压缩包内容不是同一种证据。

### 关键位置

`res/values/strings.xml` 存放字符串资源；AndroidManifest.xml 记录组件与权限等声明；classes.dex 包含 Dalvik 字节码；assets/ 与 res/raw/ 常保存额外数据。多个 classes*.dex、资源名与代码引用之间的关联也有价值。

### 文本线索

flag、CTF、错误消息和校验提示可能出现在资源或 DEX 字符串中。需要记录所在文件、字符串引用和实际执行路径，以排除未使用常量和诱饵。

### Flutter / Dart AOT

源文 Blutter 示例针对 arm64-v8a 构建，目标是恢复 Dart AOT 的函数、对象与数据结构。ABI 和构建版本关系到布局，native 层与 Dart 逻辑不能混同。

### HarmonyOS HAP/ABC

HAP 是包，ABC 是待恢复的字节码对象。原 abc-decompiler 示例区分图形入口和批量入口、auto 与 simple 的表示模式；知识重点是某模式失败不一定表示全部结果不可用，已恢复的 sources 仍可能有价值。不同配置产生的材料应保持版本和来源独立，不保留命令行或菜单。

## .NET

### IL、元数据与源码近似

dnSpy、ILSpy、dotPeek 是原文的历史表示名称，对应 IL/元数据反编译与状态观察。反编译可读性不等于逐字恢复原源码。

### NativeAOT

System.Private.CoreLib 字符串、重组后的类型元数据，以及带长度前缀的 UTF-16 数据可以提示 NativeAOT。它与普通 IL 包的处理条件不同；仅因出现 .NET 字符串不能假设存在完整 IL。

### XOR、Base64 与 AES-CBC 两阶段案例（Codegate 2013）

原例将多次 XOR（0x25 与 0x58，可合并为 0x7D）的结果作 Base64 解码，再交给 AES-256-CBC。技术证据是字节数组、各阶段数据类型、密钥来源，以及 RijndaelManaged 的 Key/IV 赋值关系。原文给出 Key 与 IV 使用同值的案例，但 AES 的块大小为 16 字节、AES-256 密钥为 32 字节，因此“同值”必须进一步核对实际截取或派生；原代码的字节串与长度也不自洽，不能照抄为可用实现。具体密钥字面量已移除。

```text
D1[i] = encrypted[i] XOR (0x25 XOR 0x58)
D2 = Base64Decode(D1)
P  = CBC_inverse(D2, 实际密钥参数 K, 实际初始化向量 IV)
验证：参数长度、填充规则、输出长度与比较关系
```

## 压缩壳与打包

### UPX

UPX 标记、节布局与解压入口支持压缩壳假说；解压前后字符串与代码布局应对应。

### 自定义壳

核心材料为解压 stub、解压后原始入口 OEP、内存中的代码和导入，以及恢复后的 PE/ELF 头。文件头修复应有映射证据，不能仅凭反编译器能够打开就认定正确。

### PyInstaller

可执行封装可能包含 Python 运行时、归档与 `.pyc`；提取后的目录名只是原示例输出，真实对象是归档结构、Python 版本及 code object。

## LLVM IR

### IR、汇编与目标对象

LLVM IR 可以转为目标汇编和对象文件；有意义的对应是 IR 中位宽、控制流和调用语义如何映射到目标架构。汇编语法偏好不是算法属性。

## RISC-V 案例（EHAX 2026）

源例是静态链接且 strip 的 64 位 ELF，并混合 RISC-V 压缩指令。入口由 e_entry 与加载映射确定；例中的 0x10000 不是通用文件偏移。2 字节压缩指令与 4 字节标准指令混合，错误模式会破坏全部边界。

常见模式包括 li 装立即数、mv 移动、auipc/jalr 组合调用、beq/bne 与 zero 比较、sd/ld 的 64 位读写和 addiw 的 32 位字运算。RISC-V 没有 x86 式 flags 寄存器，比较条件包含在分支中；a0–a7 是参数，a0 为返回值，s0–s11 为被调用者保存。

诱饵字符串、rdtime 的时间约束和递增密钥 XOR 是原案例线索：`D[i] = C[i] XOR low8(K) XOR 0xA5`，每次 K 增加 7。跨架构状态解释还依赖相应 sysroot 与系统调用语义，不保留模拟启动命令。

## 多种中间表示（历史名称 Binary Ninja）

HLIL、伪 C、伪 Rust、伪 Python 可以提供同一函数的不同表达。函数名、起始地址、IL、原指令和交叉引用应能相互定位。源文的启动速度、API 或免费版评价是历史产品背景，不是方法正确性的证据。

## 反编译结果对照（历史名称 Dogbolt）

原资料列举 Hex-Rays、Ghidra、Binary Ninja、angr、RetDec、Snowman、dewolf、Reko、Relyze。对照目的在于发现类型恢复、间接调用、分支或结构化循环的不同解释。多个反编译器一致也可能共享错误，最终仍由指令和行为支持；不保留上传或 API 调用代码。

## 证据与故障定位

基本材料包括文件类型、保护属性、节和段、符号、字符串、反汇编、IR、运行时映射与输入输出。常见故障源是架构/端序/模式错误、基址混淆、Python 版本不符、缺少栈或全局状态、算法参数长度不一致、反编译器误判数据为代码。报告应记录这些条件和已排除的假说。

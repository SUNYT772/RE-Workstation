## 场景分类
JS 签名

## 目标概述
还原某 Web 应用接口的 `sign` 参数生成算法，实现本地复现。

## 观察、决策与验证

1. 浏览器抓包 → 发现 POST 请求带 `sign` 和 `timestamp` 参数
2. 搜索 JS 源码中的 "sign" → 定位到 webpack 打包的 chunk 文件
3. 在 sign 赋值处下断点 → 命中，查看调用栈
4. 调用栈回溯 → 找到签名函数（在某个 webpack module 中）
5. 分析签名逻辑：`sign = HmacSHA256(sorted_params + timestamp, secret_key)`
6. 密钥来源：硬编码在另一个 webpack module 中
7. 本地算法对照结果为 生成的 sign 与浏览器一致
8. 验证：用复现的 sign 请求接口 → 返回正常数据

## 失败路径与诊断

| 问题 | 原因 | 解决方案 | 耗时 |
|------|------|---------|------|
| 搜索 "sign" 结果太多 | webpack 打包后变量名被压缩 | 改为搜索 `sign=` 或在网络面板找到请求后用 initiator 回溯 | 15min |
| 断点命中但看不懂代码 | webpack 压缩 + 变量名混淆 | 用 Chrome 的 Pretty Print 格式化，再配合 SourceMap（如果有） | 10min |
| 本地复现结果不一致 | 参数排序方式不对 | 仔细看源码中的 sort 逻辑（按 key 字母序 + 特殊字符处理） | 30min |
| timestamp 精度不对 | 服务端用秒级，我用了毫秒级 | 秒级时间戳而非毫秒级 | 5min |
| 密钥找不到 | 密钥在另一个 chunk 文件中通过 require 引入 | 运行时变量与跨 chunk 依赖提供密钥来源证据，实际值脱敏 | 10min |

## 能力与格式知识


- 请求 initiator、调用栈、断点与源码搜索提供不同定位证据；源素材中 initiator 缩小了签名相关调用范围，效率描述仅适用于该素材。
- 格式化代码与断点将 Webpack 打包结构和运行值对应；SourceMap 存在时，映射内容是否与当前产物一致仍是前提。
- Node.js crypto 在原素材中承载算法复现，关键是输入字节、编码、拼接顺序、密钥和时间戳与原请求一致，不规定运行环境。

## 技术机制与证据


纯算法知识：参数按 key 字母序排列，逐项形成 key=value，再以 & 连接；追加 &timestamp=〈秒级时间戳〉，以〈签名密钥〉计算 HMAC-SHA256，并以十六进制表达。排序、特殊字符、编码、拼接分隔符、秒/毫秒和输出大小写都会影响逐字节一致性。源 Node 调用与示例密钥已改为算法说明。


## 可迁移经验


- Webpack chunk 间的模块依赖与初始化顺序可解释抽取片段为何缺少运行上下文。
- HMAC-SHA256、MD5 与自定义变换的识别依据是输入关系、输出长度、编码和交叉引用；仅凭输出外观不足以判定具体算法。

## 算法与结构

**JS 签名逆向标准流程**：

签名请求、initiator/调用栈、函数参数、拼接与密钥来源、本地结果和服务端接受结果组成验证链。断点和 SourceMap 帮助把压缩后的调用映射回语义；没有 SourceMap 仍可保留调用与参数证据。


**常见签名模式**：

HMAC-SHA256 表达带密钥完整性；MD5 与盐/时间戳是原旧式模式；AES(JSON) 是加密而非签名；RSA sign 属于非对称签名。源“最常见/少见”仅是经验分布，算法识别以实际代码和输入输出为准。

## 场景分类
固件 / IoT 安全

## 目标概述
一台中低端家用路由器，从厂商网站拿到 firmware bin，用 binwalk 提取 squashfs，再用串口接到设备 UART 拿到 root shell，分析其 Web 管理界面与启动脚本。

## 观察、决策与验证

### 第 1 部分：固件分析

1. 下载固件文件（厂商官网 / OpenWRT / 自己 dump 闪存）
2. 基础识别
   
固件识别关注容器/私有头、LZMA 压缩、SquashFS 文件系统和 U-Boot。熵图表示区域随机性，不能仅凭高熵区分压缩与加密。

3. 提取
   
解包结果应保留原始固件摘要、区域偏移、文件系统类型和提取树对应关系，目录为空可能来自私有头或不受支持格式，而非固件没有内容。

4. 静态分析关键点
   
账户数据库、CGI/Web 服务、rcS/init.d、telnetd/BusyBox 字符串及管理/调试特征组成静态线索。普通功能与后门需要结合控制流、配置和认证解释，凭证/私钥值不保留。

5. 拿到 `/etc/shadow` 离线破：
   
固件账户哈希与设备实际身份之间需要验证来源和有效性，原离线口令调用与字典不保留。


### 第 2 部分：硬件 UART

1. 拆机看 PCB → 找 4 针 / 6 针未占的接口（通常未焊或焊有针脚）
2. 用万用表识别
   - GND（连接地铜片）
   - VCC（3.3V，启动时稳定）
   - TX（启动时电平跳变较多，向 UART → PC 方向输出）
   - RX（启动时基本不变）
3. 接 USB-TTL 转换器（CP2102 / FT232）
   - 路由 TX → USB-TTL RX
   - 路由 RX → USB-TTL TX
   - 路由 GND → USB-TTL GND
   - **不接 VCC**（设备自供电）
4. 串口输出的参数与可读性观察
   
串口设备、波特率、数据位、停止位、校验和电平共同决定输出可读性。原初始值 115200 属于案例参数，输入为空或乱码各有不同电气/配置原因。

5. 上电启动 → 看 U-Boot 输出 → Linux 启动 → 通常进入 login 提示
6. 原账户来源与实际登录身份相互验证，不保留凭据尝试

## 失败路径与诊断

| 问题 | 原因 | 解决方案 | 耗时 |
|------|------|---------|------|
| binwalk 提取后是空目录 | 部分固件用了非标准格式（厂商私有头） | 私有头与文件系统偏移需要对应，格式支持差异解释提取失败 | 1h |
| 原归一化熵图接近 1 | 整体加密 | 升级组件可能承载解密来源，密钥值不记录；高熵也可能来自压缩| 数小时 |
| UART 看不到任何字符 | 波特率不对 | 试 9600 / 38400 / 57600 / 115200 / 460800 / 921600 | 30min |
| UART 看到字符但是乱码 | TX/RX 接反 / 电平不匹配 | 发送/接收方向与 3.3V/5V 电平差异需独立确认，错误电平可能损坏设备 | 30min |
| login 提示但无密码可用 | 没破出来 + 厂商默认密码已改 | 启动参数与登录认证路径存在不同边界，原登录替代操作不保留 | 1.5h |
| U-Boot 没有按键中断响应 | 厂商关闭了 console / 改了 prompt | bootdelay、console 与 prompt 配置影响交互窗口；原物理故障触发方案不保留 | 数小时 |
| 进了 root 但 telnetd 不工作 | 镜像里没 dropbear/telnetd | 极简镜像缺少服务组件，权限成立与服务存在是不同事实，不保留拷入部署操作 | 1h |

## 能力与格式知识


- unblob 与 binwalk 在原素材中代表格式识别和递归提取；“更强”与私有头兼容性须看具体镜像，不能从产品名保证覆盖。
- firmware-mod-kit 表示文件系统解包/重建；firmwalker 表示提取后凭据、私钥、URL 与可疑二进制线索的归纳。
- EMBA 的源能力包括综合审计、二进制 CVE 线索与模拟启动；FirmAE/QEMU 表示固件动态环境，外设和架构差异可能使模拟结果不同于真机。
- ChirpStack USB-TTL、Bus Pirate、Tigard、CP2102 在原素材中作为串口硬件历史名；电平、引脚、地线和实际串口输出才是观察条件，不作采购或依赖建议。

## 技术机制与证据

固件审计一条龙：


原固件审计串联提取、敏感线索、模拟启动和 Web 行为。知识保留输入产物、架构/依赖、静态与动态对照，不保留仓库获取、容器启动或扫描调用。


UART 自动尝试常见波特率：


原波特率候选为 9600、19200、38400、57600、115200、460800、921600；可读启动日志是配置正确的一项证据，不保留自动尝试循环或串口调用。


U-Boot 单用户 bypass 经典招：


U-Boot 的 console、root、rootfstype、init 等启动参数影响内核和初始用户态。源例绕过登录的含义是启动参数可能改变认证路径；本页保留参数与信任边界，移除具体设置、保存和启动命令。


## 可迁移经验


- 固件镜像、文件系统、CPU 架构和动态 Web 行为分属不同证据层；提取成功不等于系统能够模拟启动。
- UART、JTAG、SWD 的接口角色需区分；本例可迁移条件是电压、引脚识别、波特率和启动输出，不能把接口存在直接等同于 root 权限。

## 算法与结构

**IoT 安全测试 4 阶段**：


软件（固件/文件系统/凭证与模拟）、硬件（UART/JTAG/电平）、启动调试（日志/配置）、系统服务（Web CGI、UPnP、mDNS、蓝牙）是原四类观察面。权限与服务行为需要独立证据，不形成拿 root 后的执行清单。


**默认凭据速查**（厂商常见）：


原默认凭据表反映多厂商沿用固定初始账户/口令的风险。账户和口令统一为〈默认管理员身份〉/〈默认秘密〉；是否仍有效、是否强制更换、设备间是否复用才是可迁移知识，不保留猜测列表。

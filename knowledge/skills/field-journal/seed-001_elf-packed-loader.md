## 场景分类
二进制分析

## 目标概述
分析一个伪装成 .sh 脚本的 ARM64 ELF 自解压加载器，还原其解压算法和 payload 注入流程。

## 观察、决策与验证

1. 文件头证据确认真实类型（ELF，非 shell 脚本）
2. 程序头观察 → 发现第 3 个 PHDR 被故意损坏（0x0a 填充）
3. 容错解析获得架构（AArch64）、入口点、编译器信息
4. IDA/Ghidra 加载 → 从入口点开始分析
5. 识别出 LZSS 解压循环（位流操作 + 滑动窗口回拷）
6. 识别出 mmap → 解压 → mprotect → 跳转的注入流程
7. 用 Python 重写解压器，dump 出 payload
8. 分析 payload 内容（包含 /proc/self/exe 引用，说明是进程注入器）

## 能力与格式知识


- 文件头与结构字段比后缀更能支持格式判断；损坏 PHDR 的场景中，源素材比较了严格与容错解析，后者保留的结构仍需交叉验证。
- ARM64 位操作密集时，反编译表达与指令级 carry、移位、寄存器宽度之间可能有差异，汇编是核对算法语义的证据。
- Python struct 在原素材中承载字节序和字段解码，手写解压器承载位流/回填语义的复现；这是能力说明，不规定实现环境。

## 技术机制与证据


类型证据为 ELF 64-bit LSB、AArch64，原伪装后缀为 shell 脚本。压缩区示例文件偏移为 0xa6a24、长度 1981 字节；虚拟地址换算示例为 0x3d66bc − 0x330000 = 0xa66bc。提取区域与地址换算是两个证据，不能把它们误作同一位置。原样本文件名改为〈加载器样本〉，命令不复制。


LZSS 核心分为位流读取、字面量与匹配回拷。源简化片段仅给出初始 shift_reg=0x80000000，未给完整解压算法；本页保留该初态及下述 refill 的关键返回语义，不补造实现。


## 可迁移经验


- 自定义压缩的识别依据包括输入位流、literal/back-reference、长度和偏移关系；不能只凭常见压缩格式名称下结论。
- ARM64 的 dc cvau / ic ivau 属于缓存维护语义，和 syscall 表中的系统服务是不同层次；重建后执行异常可涉及缓存一致性。
- 汇编算法转为知识伪代码时，寄存器宽度、carry、refill 时机和返回位要分别保持。源素材中的错误解压输出是这些差异的反例。

## 算法与结构

**识别自解压 ELF 的标准模式**：

自解压行为模式包括入口初始化、解压函数、可写映射、解压内容、可执行权限与控制流目标。mmap 区域、mprotect 前后权限和入口偏移构成关联证据，不提供载荷注入流程代码。


**ARM64 位流读取的通用模式**：

ARM64 位流模式通过 32 位移位寄存器左移与 carry 表达当前位；耗尽后的 refill 需要恢复输入字和新最高位。源例强调 adcs 与 adds 的差异，refill 返回新加载字 bit31，错误实现会污染整个输出。

## 场景分类
渗透测试 / Web RCE

## 目标概述
某 Java Web 应用使用受影响版本的 Log4j2（原文以 <2.17.0 概括范围，未区分各 CVE、分支修复与运行配置），可控字段是否进入易受影响的日志查找路径决定触发条件，原文将其概括为 JNDI 远程加载，构造 LDAP/RMI 服务推送恶意类拿到目标机执行权限。

## 观察、决策与验证

1. 目标识别
   - HTTP 头 `Server`、`X-Powered-By` 含 Java 应用框架（Tomcat/Spring/Liferay）
   - 版本指纹：登录页、404 页、路径泄露
   - 漏洞确认：通过任意可被记入日志的字段（User-Agent、Referer、X-Forwarded-For、登录用户名、搜索框）发探测 payload
2. 准备 OOB 监听
   - 带外观察平台（接收端统一为角色标识）
   - LDAP / RMI / HTTP 在对象解析中的服务角色
3. 探测有无漏洞
   
原 OOB 观察将被记录的输入字段与 DNS 回调关联。DNS 查询支持命名解析发生，不足以单独证明远程代码执行；域名和注入载荷已移除。

   原 User-Agent 等字段与 DNS 事件的关联只支持解析层结论，不等于 RCE 已确认
4. 起利用服务（自建公网 VPS 或 ngrok 反代）
   
原服务示例把 LDAP/RMI 名称解析、HTTP 内容与系统执行串联。知识上需要分开说明出站连通、对象获取、类加载或本地类行为及实际执行证据，不复制服务启动或系统命令。

5. 触发利用 payload
   
原触发串使用 JNDI、LDAP 路径与编码的命令数据，表达输入解析后可能跨到对象解析/执行边界；本页不保留载荷或编码命令。

6. 原记录声称出现系统执行影响 ；后续权限与持续状态属于独立影响范围

## 失败路径与诊断

| 问题 | 原因 | 解决方案 | 耗时 |
|------|------|---------|------|
| 探测 payload 无 DNS 回连 | 目标在内网无外网 | 原记录比较 DNS 可达范围与观察点，具体接收域和替代探测方案不保留 | 1h |
| DNS 解析了但 LDAP 不通 | 出网策略只放 DNS | DNS 与 LDAP 的出站策略不同，原失败只证明对应网络层条件未满足；外传方案不复制 | 1.5h |
| LDAP 通了但目标不加载 class | JDK 高版本（8u191+/11.0.1+/...）默认 `com.sun.jndi.ldap.object.trustURLCodebase=false` | 远程类加载与已有类行为是不同前提；原 Tomcat / Groovy / BeanFactory 仅作历史类别，不保留替代利用方案 | 3h |
| 双引号被转义 / payload 被 WAF 拦 | 各种 ${} 嵌套绕过现成的规则 | 嵌套、大小写与默认值解析造成文本规则和最终语义差异，载荷不保留 | 1h |

| Spring Boot 应用没复现 | Spring 用 Logback 不用 Log4j2 | 排查 dependency tree 看是否引入 spring-boot-starter-log4j2 | 20min |

- 原 Nuclei CVE-2021-44228 模板表示版本/行为线索的批量归纳，命中与实际受影响范围是不同结论。
- interactsh 与原公开 OOB 平台承载事件关联；托管位置、可见数据与日志留存影响隐私，原“自建更隐私”缺少具体部署证据。

## 算法与结构

**Log4Shell 探测三段法**：


多字段输入、OOB 解析、对象解析/类加载与命令执行是不同证据层，某层不可见时只能说明该条件未被观察到。原三段流程改为层级模型，不引出替代外传或利用方案。


**关键判断**：


DNS 可达而 LDAP 不达可能来自出站策略，不能直接推出 JDK 版本；LDAP 可达而未加载类可能与 trustURLCodebase 等配置有关。特殊字符与运行时解析影响命令语义，但本页不保留包装方式。原判断中混同网络与运行时的部分明确标记为结论边界。

# 二进制静态分析：框架、证据与故障经验

来源：skills/ida-reverse/SKILL.md

## 适用范围与概念

覆盖 x86、x64、ARM 等架构及 PE、ELF、Mach-O、EXE、DLL、SO、SYS、APK 中的本机代码、固件等对象。研究问题包括程序主逻辑、注册验证与口令处理、加密变换、恶意软件行为、漏洞成因。文件扩展名只是线索，实际格式和指令集以文件内容为依据；托管代码和动态验证是相关的独立知识领域。

分析记录关注对象身份、当前分析状态和可复核证据，报告分别呈现观察与推断。这些技术目标可以用于不同实现与工作环境。

## 核心原理与技术细节

### 全局概况

概况包括架构、入口、函数总数、字符串统计、段布局、导入分类及高交叉引用函数。入口常表现为 main、WinMain、DllMain；导入可按加密、网络、文件 I/O、注册表分类。URL、路径和错误消息能够成为定位线索，高 xref 数说明被广泛引用，不能单独证明业务重要性。

概况与局部理解具有相互校验关系：已知架构和段范围可以解释反汇编，关键函数的真实调用关系又可纠正仅凭名称或导入作出的初步判断。

### 函数、反编译与反汇编

函数可以按名称、地址和范围辨识。反编译伪代码便于理解变量、条件和循环；原始指令用于核实类型、符号扩展、调用约定、分支和边界。函数综合视图包含伪代码、字符串、常量、调用者、被调用者和基本块；大小、块数与 xref 数是概貌指标。全局变量、导入、字符串与命名符号可以独立索引，分页和名称筛选是控制信息量的方式。

### 交叉引用、调用图与数据流

“谁引用目标”与“目标引用谁”是两个方向；数据引用和控制流引用也需区分。调用图表示函数间结构，多个根和深度范围决定局部图边界。反向数据流回答参数或值从何而来，正向数据流回答其影响哪些输出；图中出现连边不等同于该路径在特定输入下可达。

### 搜索与读取

字符串搜索可围绕 URL、文件路径、error/fail/invalid、key/password/secret/token 等语义；指令文本、立即数与字节模式提供不同索引。字节签名中的通配符表达不稳定位置。读取结果包括原始字节、编码字符串、指定位宽整数、全局值和结构体字段，结论依赖地址、长度、类型、字节序和编码。

### 类型系统、栈帧与签名

结构体、枚举、联合体和函数原型能把无类型读写恢复为字段语义；类型推断属于待校验解释。栈帧记录变量偏移、名称与类型，可用于核实局部缓冲区边界。地址签名、完整函数签名与引用位置签名分别定位代码点、函数和引用特征，唯一性需要限定版本与搜索范围。

### 注释、命名、代码边界与修改记录

函数、全局变量、局部变量与栈变量的语义命名应保留依据；追加注释与覆盖注释代表不同的知识维护语义。代码/数据边界、函数定义和取消定义影响后续反汇编结果。汇编级与字节级修改表达同一底层变更的不同层次，记录中应能还原原始位置、旧值、新值、假设和可观察差异，而不是仅留下“成功”的结论。

### 数值与可交换输出

进制转换的关键是十六进制/十进制、位宽、符号和端序一致，不依赖某个专用转换入口。函数结果可表示为 JSON、C 头文件和原型清单。段名、函数范围与批量索引是数据库内容，原脚本接口只是获取这些信息的历史方式。

## 故障定位与经验

### 客户端 schema 不一致

原记录出现 `Structured content does not match the tool's output schema`：客户端对结构化返回的验证与实际结果不一致，不能据此认定样本无效。记录区分了远程 HTTP 与本地 stdio 两种传输，二者都曾遭遇验证问题。历史 issue #388 与 PR #389 涉及 HTTP structuredContent 的部分修正；这属于当时版本经验，不是当前兼容性承诺。技术判断需要区分传输成功、返回字段验证、数据库已打开和当前上下文已绑定。

### 路径权限与文件身份

System32 路径在原环境中曾不可直接读取。只读原件与可读副本是同一样本的不同载体，身份核对需关联文件名、哈希、路径、架构和副本来源。临时副本能够隔离路径权限与分析库问题，但文件名改变不代表二进制内容改变。

### 分析库锁与孤儿 worker

超时请求之后，子 worker 可能仍持有 `.id0`、`.id1`、`.nam`；相关数据库伴随文件还包括 `.til`、`.i64`。后续打开失败甚至 GUI 中的“权限不足”可能是文件锁，而非目录权限。进程树、锁持有者和库文件身份是定位证据。原运行方案曾通过结束完整进程树、隔离旧库和使用带 GUID 前缀的临时副本避免冲突；这里保留故障机制与隔离目标，不提供进程终止或清理命令。

### 长时间自动分析与超时

打开请求未返回，并不意味着后台分析停止。原记录中 Snipaste.exe 带自动分析约 324 秒才成功；600 秒上限和每 10 秒进度提示是该环境的经验数值，不是通用时间限制。大型 GUI 样本和复杂程序更容易出现这一现象；跳过自动分析得到的可用数据库也可能仍不完整。

区分“请求超时”“worker 存活”“会话可见”“自动分析完成”四种状态，有助于解释长时间无响应。原状态文本 `INFO:opening:已用时/上限` 表示活动进度，`OK:文件名:session_id` 表示目标会话已可见，`(temp copy)` 表示使用副本，`ERR:open_timeout_xxs` 表示等待达上限。这些是历史日志格式，而非本模块要求的调用协议。

### 绑定、健康与就绪

`No database bound` 对应上下文没有绑定数据库；`Failed to open database` 可能涉及被锁的旧库。多文件对比中，当前会话、会话标识和文件身份不能混淆。资源关闭、数据库保存、worker 健康、服务健康、字符串缓存和反编译子系统就绪是相互独立的观察面。后台日志持续输出可能仅是前台等待方式的问题。

传输与客户端兼容性、数据库绑定和分析子系统就绪分别核对，有助于将接口层故障与样本解析问题区分开。

## 观察项与判断依据

### 关键函数理解

一份有用的函数解释应同时呈现入口条件、关键分支、数据来源、调用关系和返回含义。伪代码与反汇编的差异可以揭示类型误判；字符串引用与常量用于定位，但需回到真实路径。

### 混淆与库代码

字符串加密、导入哈希和控制流平坦化会遮蔽语义；其恢复目标分别是明文含义、实际外部调用和可解释控制流。C++ STL 等库代码可能占据大量函数，FLIRT/Lumina 是历史库识别概念，用于区分库逻辑与业务逻辑。恢复成功应由可读语义和一致引用证明，不能仅由名称变好看证明。

### 验证、CTF 与漏洞定位

注册/序列号相关字符串可指向验证条件，输入变换与比较点才是算法证据。CTF 类问题关注架构、入口、判断分支和输入变换的逆向解释。危险字符串处理导入仅是漏洞候选；缓冲区大小、长度计算和用户可控路径共同决定风险。原“不要暴力破解”提示承载的是以反汇编和数学变换推导结论的判断依据，本页不规定任务执行方法。

## 证据与报告结构

报告可包括：样本与数据库身份、架构/段/入口概况、关键函数及地址、调用关系、字符串/常量、前后向数据流、类型与栈帧、边界条件、观察到的行为、尚未验证的推断和限制。若存在修改，另列原始与修改后内容、位置及行为差异；若存在副本或分析未完成，注明其影响。

证据质量可从五方面复核：结论能否追溯到样本与位置、数值是否一致、核心路径是否得到解释、数据库状态是否清楚、发现能否复核。
